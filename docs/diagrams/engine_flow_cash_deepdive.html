Why this matters

The two failure modes we prevent
  • GFV (Good Faith Violation): buying with funds from a sale that hasn't settled yet, then selling the new position before those funds settle. 3 GFVs in 12 months → 90-day settled-cash-only restriction by the broker.
  • Double-spend race: two signals fire in the same tick window. Both call get_balances before either order is registered server-side. Without a reservation ledger, both gates see the same cash and approve.
Exit path — never blocked by cash
  • Sells generate cash → no GFV from a close
  • _preview_or_abort only runs the cash gate if side == 'buy'
  • Existing positions remain closeable even when:
    • cash is zero
    • account daily-loss cap is breached
    • user role was demoted mid-session
What's NOT in our gate (intentionally)
  • No buying-power calc — we're cash-only, no margin
  • No PDT counter — settled-cash accounts aren't subject to PDT
  • No GFV counter — we just never allow the conditions for one

Cash reservation ledger — lifecycle

Process-scoped, in-memory, UUID-keyed · class attr on OrderManager · survives nothing across restarts (broker is source of truth on restart)

Worked example — buy 2 SPY 0DTE calls @ $1.50

T0 Signal generated · qty=2, est. premium $1.50
T1 Tradier preview_order returns:
cost = 2 × 100 × $1.50 + commission + fees = $300.00 (prod) | $300.00 (sandbox)
T2 Fetch balances.cash.cash_available from Tradier
settled_cash = $1,000.00
If cash block is absent (non-cash account, sandbox quirks), falls back to total_cash and logs a warning.
T3 Sum active reservations for this user (purges expired first)
active_reservations = $0.00 (none pending)
T4 Compute required & effective
fee_buffer = qty × $0.65 = $1.30 (sandbox) | $0.00 (prod, fees already in cost)
required = cost + fee_buffer = $301.30 (sandbox) | $300.00 (prod)
effective_avail = settled_cash − active_reservations = $1,000.00
T5 Decision: $301.30 ≤ $1,000.00 → APPROVE
reservation_id = uuid4() · expires_at = now + 60 s · amount = $301.30
Inserted into _pending_buy_reservations class dict.
T6 (concurrent) Second signal fires same tick — wants $400 buy
settled_cash = $1,000.00 (Tradier hasn't reflected our T5 order yet)
active_reservations = $301.30 (from T5 — still held)
effective_avail = $698.70 ← shrunk by reservation
$400 ≤ $698.70 → APPROVE second buy as well
Had T6 been $750, it would have been REJECTED. No double-spend.
T7 Tradier fills the T5 order · Trade + Position rows written · notification fires
T8 finally: release reservation UUID
_pending_buy_reservations.pop(reservation_id, None)
Runs on every terminal outcome — filled, rejected, canceled, expired, exception. Even if the cash gate approved but the broker call later raised.

Failure-mode scenarios

A. Concurrent same-tick buys ($1k cash, two $600 buys)
1st: approved, reserves $600. 2nd: sees $400 effective → rejected. No double-spend on $1,000 of settled cash.
Outcome: at most one of the two fills. ✓
B. Approved but broker call raises
Preview OK, reservation acquired, then place_order throws (network, rate limit). finally: releases the UUID immediately.
Outcome: cash freed up for next signal. No orphan reservation. ✓
C. Process crashes after acquire, before release
Class dict is in-memory only — full restart wipes all reservations. If just the calling task dies, TTL kicks in after 60 s, the next sum-call purges and logs a warning.
Outcome: cash gets unlocked at most 60 s late. ✓
D. Just sold for $500; immediately try to buy with that cash
Tradier's cash.cash_available reflects only settled cash. Until T+1 settlement, the $500 isn't in cash_available — our gate sees no $500.
Outcome: buy rejected. GFV scenario impossible. ✓
E. Sandbox env, preview returns commission=0/fees=0
fee_buffer = qty × $0.65 is added so the gate behaves like prod. Without it, a sandbox-approved buy could fail at the edge of settled cash in live.
Outcome: dev/test parity with prod. ✓
F. Strategy demoted mid-session (user → viewer)
Next buy: role gate rejects (line 421). Existing position: close_position doesn't run the role gate or the cash gate. Open position can still exit on SL/TP/time.
Outcome: open trades remain closeable. ✓

Verify — circle which scenario applies, write any concern

Reservation amount = required (cost + fee_buffer), not just cost. Matches what the broker will debit. TTL of 60 s · short enough for fast unlock, long enough that normal fills (1–5 s) finish well before expiry. Process-scoped: if you run multiple worker processes, each holds its own ledger. This is a gap if you scale out. Tradier's cash.cash_available is authoritative — verify it on the live account before relying on this gate. Sells never enter this gate — confirmed by reading line 299 (if side == "buy":).

Cash-gate stress test against these params

SPY worst case: 2 positions × $500 = $1,000 reserved. Needs ≥$1,000 settled cash to open both. TSLA worst case: 1 position × $400 = $400 reserved. Single-name concentration intentional. Both running together: $1,000 SPY + $400 TSLA = $1,400 max reservation at once. If account is $2,000 settled: 70% of cash can be reserved. Buffer left for next signal? After full SL hit (lose 50% of $500 = $250 on SPY, 40% of $400 = $160 on TSLA): cash drops to ~$1,590 but unsettled until T+1. Account-wide daily loss cap should trip before you lose enough to risk GFV from re-deployment urgency.
